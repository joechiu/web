# Tool4 — Validation / Language / Compliance

## Overview

Tool4 validates the draft output produced by Tool3 against configured rules, approved evidence, language requirements, tone, compliance, formatting, and business policy.

Tool4 uses a multi-stage validation flow. Each stage produces an outcome that is passed to the Decision Router to determine the final result.

---

## Inputs

Tool4 accepts the following inputs:

### Draft Output

The customer-facing draft content generated by Tool3.

```json
{
  "draft_output": "Our customer support team is available Monday to Friday from 9:00 a.m. to 5:00 p.m."
}
```

### Approved Evidence References

Evidence that may be used to support factual claims in the draft.

Each evidence item contains:

- `id`
- `description`
- `approved`

```json
{
  "approved_evidence_references": [
    {
      "id": "EVID-001",
      "description": "Customer support is available Monday to Friday from 9:00 a.m. to 5:00 p.m.",
      "approved": true
    }
  ]
}
```

Only approved evidence should be used for factual claims.

### Language Level Requirements

Defines the required language level using CEFR.

```json
{
  "language_level_requirements": [
    "Plain English",
    "B1 minimum",
    "B2 maximum"
  ]
}
```
### CEFR Language Level
Here's the content as a Markdown table:

| Level | Category | Level Name | What You Can Do |
|---|---|---|---|
| A1 | Basic User | Beginner | Can understand and use familiar everyday expressions and very basic phrases. |
| A2 | Basic User | Elementary | Can communicate in simple, routine tasks requiring a direct exchange of information. |
| B1 | Independent User | Intermediate | Can handle most situations while traveling and produce simple connected text on familiar topics. |
| B2 | Independent User | Upper-Intermediate | Can interact with a degree of fluency with native speakers and understand complex technical texts. |
| C1 | Proficient User | Advanced | Can express ideas fluently without searching for words and use language flexibly for social/academic tasks. |
| C2 | Proficient User | Mastery / Fluent | Can understand virtually everything heard or read with ease and express subtle nuances precisely. |

### Tone Rules

Defines the required communication style.

```json
{
  "tone_rules": [
    "Professional",
    "Clear",
    "Helpful",
    "Neutral",
    "Do not use aggressive language",
    "Do not use informal slang",
    "Do not use overly technical language",
    "Do not make misleading claims"
  ]
}
```

### Compliance Rules

Defines mandatory compliance requirements.

```json
{
  "compliance_rules": [
    "Do not include unsupported regulatory or legal claims.",
    "Do not include confidential or sensitive customer information.",
    "Do not make claims that are not supported by approved evidence.",
    "Do not provide guarantees unless explicitly supported by approved policy."
  ]
}
```

### Formatting Rules

Defines formatting requirements.

```json
{
  "formatting_rules": [
    "Use clear paragraphs.",
    "Use complete sentences.",
    "Use readable formatting."
  ]
}
```

### Business Policy Rules

Defines business-specific requirements.

```json
{
  "business_policy_rules": [
    "Content must align with approved business policy.",
    "Only approved evidence may be used for factual claims.",
    "Customer-facing content must use professional language."
  ]
}
```

Business policy validation is performed by the LLM validation stage.

### Preview Status

Indicates the result of Pre-Validation.

```json
{
  "preview_status": "C"
}
```

Supported values include:

- `""` — NONE
- `C` — CLEAR
- `E` — ESCALATE

The Preview Status controls the initial routing of the validation flow.

---

## Validation Flow

The main validation stages are:

1. `inputs_validator`
2. `fast_rule_validator`
3. `fast_gate`
4. `configurable_rules`
5. `unified_llm_validator`
6. `unified_llm_result`
7. `decision_router`
8. `tool4_validation_output`
9. `fail_report`

### Pre-Validation Routing

The `preview_status` from Pre-Validation determines how the flow starts.

- If the input is `C` (CLEAR), validation continues through the normal validation pipeline.
- If the input is `E` (ESCALATE), the flow is escalated and downstream validation stages are skipped as appropriate.

---

## Node Responsibilities

### Node 1 — Inputs Validator

Determines the initial routing based on the Pre-Validation result.

It identifies whether:

- The submission is an initial submission.
- Human review is required.
- Fast validation should run.
- The flow should continue to configurable rules.
- The flow should escalate.

### Node 2 — Fast Rule Validator

Performs deterministic validation of fast rules.

Examples include:

- Minimum length.
- Maximum length.
- Banned words.
- Regex patterns.
- Other deterministic checks.

A blocking result from this node prevents downstream validation nodes from executing.

### Fast Gate

Controls whether downstream validation is executed.

- If Node 2 passes, the flow can continue to configurable rules and LLM validation.
- If Node 2 blocks or escalates, downstream validation is skipped.

### Node 2.1 — Configurable Rules

Validates configurable deterministic rules supplied through the input.

This node is separate from the LLM-based business rule validation.

### Node 3 — Unified LLM Validator

Performs semantic validation that cannot reliably be handled by deterministic rules.

This includes:

- Evidence grounding.
- Compliance.
- Tone.
- Language level.
- Formatting.
- Business policy.
- Quality and logic.
- Suggested corrections.

Business rule validation is performed by the LLM in this stage.

### Node 3.1 — Unified LLM Result

Processes and normalizes the LLM validation result for downstream decision making.

### Decision Router

Combines the relevant node outcomes and determines the final decision.

Possible decisions include:

- `P` — PASS
- `R` — REVIEW_REQUIRED
- `B` — BLOCK
- `E` — ESCALATE

### Tool4 Validation Output

Produces the final structured validation response.

It contains the final decision, validation findings, quality information, evidence findings, compliance findings, suggested edits, and outcome trace.

### Fail Report

Provides failure or escalation information when the final validation does not pass.

---

## Outcome Codes

| Code | Meaning |
|---|---|
| `N` | NONE |
| `C` | CLEAR |
| `S` | SKIPPED |
| `P` | PASS |
| `R` | REVIEW_REQUIRED |
| `B` | BLOCK |
| `E` | ESCALATE |

The exact node outcome depends on the stage and routing conditions.

---

## Important Routing Rules

- A CLEAR Preview Status allows the validation flow to continue.
- An ESCALATE Preview Status causes escalation and prevents unnecessary downstream validation.
- A BLOCK from the Fast Rule Validator skips configurable rules and LLM validation.
- Configurable rules are deterministic rules handled by Node 2.1.
- Business policy validation is handled by the LLM validation stage (Node 3).
- Evidence grounding is handled by the LLM validation stage.
- Compliance validation is handled by the LLM validation stage.
- The Decision Router determines the final outcome from the active node outcomes.

---

## Project Purpose

Tool4 acts as the final validation layer for Tool3-generated customer-facing content.

Its primary responsibilities are:

- Validate deterministic rules.
- Validate approved evidence usage.
- Detect unsupported claims.
- Validate compliance requirements.
- Validate tone and language.
- Validate formatting.
- Validate business policy through the LLM.
- Route blocked and escalated cases correctly.
- Produce a consistent final validation decision.
